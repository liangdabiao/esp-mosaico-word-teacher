# word_teacher 真机联调：问题与修复全记录（2026-10-25 ~ 10-27）

> 记录 Vibe Mode 0.2 真机联调阶段遇到的所有问题、根因与修复方法。
> 供后续开发对照，避免重复踩坑。按发现顺序编号，每条含"现象 → 根因 → 修复"。

## A. 启动与显示

### A1. 应用启动即静默复位，设备反复跌回恢复模式（最耗时的问题）

- **现象**：装机后设备重启回 factory（恢复模式），应用无法驻留；日志环里应用启动到 4.9 秒后无任何输出。
- **根因**（多层叠加，逐层剥开花了多轮）：
  1. **WiFi 初始化阻塞渲染任务**：`esp_wifi_start()` 含约 30 秒射频校准，在 `wt_network_start()` 里同步执行，而它在 GSP 渲染任务已运行后调用——渲染任务被饿死触发任务看门狗复位。
  2. **启动晚期失败触发 abort**：`main.c` 里 `ESP_ERROR_CHECK(wt_runtime_start(ui))` 失败会 abort，bootloader 判定 ota_0 应用"未确认"自动回滚。
- **修复**：
  1. WiFi 拉起移入独立网络任务（8KB 专属栈，`wifi_bringup_task`，完成后自删）——不占渲染任务、不占 worker 栈；
  2. `main.c` 启动晚期失败改为降级日志，不再 abort。

### A2. 显示持续丢帧/整帧不刷新（ESP_ERR_NO_MEM）

- **现象**：日志每隔 ~180ms 刷 `spi transmit (queue) color failed` + `TE ticket N submit failed: ESP_ERR_NO_MEM`；严重时整屏冻结为静止画面（截图来自镜像帧，具有迷惑性）。
- **根因**：GSP 整帧提交 `draw_bitmap(0,0,480,480)`（460,800B，PSRAM），而 BSP 初始化 SPI 总线时 `max_transfer_sz` 仅按 8 行（7,680B）分配——SPI DMA **描述符池按该值预分配**，sct 路径每满额块需要 1（命令）+2（数据）个描述符，整帧远超池容量 → 每帧提交必然 NO_MEM。
- **修复**（BSP `onboard/display.c` 两处）：
  1. `max_transfer_sz` 提升为 64KB 分块（描述符池 ~20KB 内部 RAM）；
  2. `psram_dma_direct = true`（帧数据直通 PSRAM DMA，无需内部暂存）。
- **教训**：截图来自屏幕镜像帧，**不能作为显示正常的证据**；必须对照日志的提交错误计数。

### A3. 日志环太小导致误判"应用没跑"

- **现象**：日志快照里 app 启动 4.9 秒后"无输出"，疑似挂起。
- **真相**：`CONFIG_ESP_IRIS_LOG_RING_BYTES=4096`，WiFi/factory 的 30 秒日志把 app 日志尾巴冲掉了。app 实际健康运行（`wt_diag` 堆打点每 20 秒一条为证）。
- **教训**：判断"应用挂起"必须看日志时间戳是否持续增长，不能只看"最后一条日志多旧"。

## B. 云端与网络

### B1. TLS 握手随机失败（bad finished message / 证书验证失败）

- **现象**：`mbedtls: bad finished message`、`No matching trusted root certificate found`；同一 Key 在 PC 上全通。
- **根因**：家庭路由器对设备侧**新建 TLS 握手**有随机丢弃/损坏（多次复现，PC 同网络同 Key 全通排除服务器与 Key 因素）。
- **修复**：
  1. DashScope 改为 **keep-alive 常驻连接**：首次握手成功后所有问答复用同一条加密连接（握手次数 -90%）；失败自动销毁重建；
  2. 所有请求失败自动重试一次（2.5 秒间隔）；
  3. 复用连接上显式重置 HTTP method（上一笔 POST 会残留到下一笔 GET）。

### B2. 有道例句接口服务端 500

- **现象**：例句发音稳定 `HTTP 500`。
- **根因**：有道 `dictvoice?type=2`（整句）服务端问题，english-dict 文档同记录。
- **修复**：例句整句改走百度 `fanyi.baidu.com/gettts`（16kHz MP3，播放器 3 倍升采到 48k）。
- **遗留**：百度走 HTTPS，在本网络的弱网时段可能证书验证失败（与 B1 同源），重试机制覆盖大部分场景。

### B3. HTTPS 下载音频极慢/中途停滞

- **现象**：HTTPS 音频下载 30 秒仅 2093 字节（~70 B/s），触发 30 秒预算墙。
- **修复**：单词/例句音频 URL 全部回归 **HTTP**（公开发音接口，无密钥；english-dict 原版即 HTTP）。HTTPS 仅用于需要密钥的 DashScope API。
- **教训**：不要"顺手"把公开接口升级 HTTPS——设备证书包对部分中文站点证书链覆盖不全（`No matching trusted root certificate found`），且 TLS 握手在本网络环境下是最大的不稳定源。

## C. 音频子系统

### C1. MP3 解码器打开失败："Decoder MP3 not registered"

- **现象**：点击发音后 `AUDIO_DEC: Decoder MP3 not registered` + `Fail to open decoder MP3 ret -7`。
- **根因**：esp_audio_codec 组件的 simple_dec **默认注册表不含 MP3**（只有 WAV/M4A/TS/OGG），MP3 需要显式调用 `esp_mp3_dec_register()`——移植时漏掉了 english-dict 的这个调用。
- **修复**：`wt_voice_start()` 启动时依次调用 `esp_audio_dec_register_default()` + `esp_mp3_dec_register()`。

### C2. 最终形态：彻底绕开注册表，直连底层 MP3 API

- **背景**：注册修复后 simple_dec 仍偶发打不开（预编译库的注册表实现与 common 表不互通）。
- **修复**：完全改用 `esp_mp3_dec_open/decode/reset/close` 底层直连 API（头文件明示"只用 MP3 解码时无需注册"），解码器**开机常驻**（启动早期堆完整时 open 一次），每段流结束后 `esp_mp3_dec_reset` 复位复用。
- **教训**：`esp_audio_dec_close()` 与 `esp_mp3_dec_open()` 不配套；且关闭后必须清空句柄缓存，否则复用已关闭句柄。

### C3. I2S 全双工采样率冲突

- **现象**：`I2S_IF: Current mode playback conflict sample_rate 48000 with peer mode sample_rate 16000`。
- **根因**：麦克风（录音 16kHz）与扬声器（播放 48kHz）共用配对 I2S，采样率不一致直接冲突。
- **修复**：麦克风同样以 48kHz 打开，采集任务 3:1 抽取降为 16kHz 供 ASR（ES8311 在 16kHz 直播会失真，48kHz 是唯一健康通路，english-dict 同结论）。

### C4. 音量极小：音量曲线缺失 + open 后音量被复位

- **现象**：音频数据全部写入成功（日志 ok=1 pcm>0）但声音极小且发闷。
- **根因**：ES8311 的音量曲线（vol→dB 映射）必须在每次 `esp_codec_dev_open` **之后**安装；且 open 会复位 codec 寄存器，音量需重设。缺曲线时 `set_out_vol(50)` 落在硬件极低档。
- **修复**：`audio_set_format()` 内对齐 english-dict：open 后装 6 点曲线（0→-40dB … 100→+6dB）并重设音量。
- **注意**：音量是 NVS 持久化的用户设置——控制面板（下拉）修好后把音量拉到 100 即可。

## D. 字体

### D1. 音标全部显示为乱码

- **根因**：LearningSans 合成字体（NotoSansSC + DejaVu 补丁）**不含 IPA 音标字形**（ə ɪ ŋ ʃ ˈ ˌ 等约 19 码点），子集化后依旧缺失。
- **修复**：从 `D:/esp/fontsrc/ipa/NotoSans-VF.ttf`（SIL OFL）静态化后**字形级合并**进 LearningSans-Full，再子集化（1.26MB，词库全字符 + GB2312 一级字表 + IPA + 希腊字母全覆盖）。工具：`tools/build_font.py`（含字形移植脚本逻辑，见 git 历史）。
- **教训**：fontTools.merge 对含 VarStore 的字体会抛异常；先实例化+剥离 layout 表再 merge 可行。

## E. UI 场景

### E1. 下拉面板/设置页完全无法使用（z-order）

- **根因**：新增的词书/词条/测验页容器追加在场景数组末尾，GSP **后渲染者在上层**——覆盖层（下拉面板/设置页/错误页）被压在这些页面之下，拉下来不可见、不可点。
- **修复**：`tools/fix_zorder.py` 把设置页/错误页/状态标签/形状/下拉面板的子树整体移到数组末尾（置顶）。
- **教训**：GSP 场景追加新页面容器时，覆盖层必须保持在数组末尾。

### E2. 首页标题与卡片重叠

- **根因**：场景改造时清空了旧标签文字但遗留对象，与书卡层叠。
- **修复**：`make_ui.py` 重跑清理逻辑（遗留标签文字置空）。

## G. 第三轮真机联调（例句/音量/面板）

### G1. 例句发音失败：三层原因依次剥离

- **第一层**：有道 `dictvoice?type=2`（整句）服务端稳定返回 500（2026-10 起持续，english-dict 文档同记录）。
- **第二层**：切百度 `fanyi.baidu.com/gettts` 后仍失败——设备 x509 证书包**不含百度证书链**，`No matching trusted root certificate found` 100% 复现；且百度对 HTTP 强制 301 跳 HTTPS，无法绕开。
- **第三层（最终方案）**：整句改走 **DashScope qwen3-tts-flash**，复用问老师朗读的 keep-alive 常驻连接——该连接已长时验证稳定，无需新建握手。缓存层 `s:` 前缀保留在播放器侧。
- **教训**：外部免费 TTS 端点可用性随时变化；有已验证的付费通路时，例句这类低频功能直接走已验证通路更省心。

### G2. 复用连接未更新 URL（keep-alive 引入的新问题）

- **现象**：keep-alive 修复后，单词发音正常，但 TTS/其他路径随机失败。
- **根因**：`esp_http_client` 复用连接时不会自动更新目标 URL——TTS 请求体被发到上一次的 chat 路径。
- **修复**：`exchange_once` 在 `api_client_get` 后显式调用 `esp_http_client_set_url(client, url)`。

### G3. 单客户端按主机切换即销毁（握手失败率放大）

- **现象**：单词（OSS 下载）→ 问老师（DashScope）→ 例句 TTS 每次主机切换都重新握手，而本网络新建握手约半数失败。
- **修复**：`api_client` 单句柄改为 **3 槽位按主机保留**（DashScope 与音频 OSS 各占一条互不挤掉），失败按主机销毁重建；握手失败自动重试递增 3 次。

### G4. 下拉面板/设置页完全无法使用（z-order）

- **现象**：顶部下拉无反应；设置页不可进/不可用。
- **根因**：新增的词书/词条/测验页容器追加在场景数组**末尾**，GSP 后渲染者在上层——把下拉面板（quick_settings）、设置页（settings_panel）、错误页、状态标签全部压在下面。
- **修复**：`tools/fix_zorder.py` 把覆盖层子树整体移到数组末尾置顶。
- **教训**：GSP 场景追加新页面容器时，覆盖层必须保持置顶（数组末尾）。

### G5. 声音极小

- **根因**：控制面板默认音量 50，音量曲线上 50 ≈ -20dB（很轻）；且设备 NVS 已保存该值。
- **修复**：默认音量 80（曲线 0dB 满档）；面板音量滑块（z-order 修复后可用）拉到 100 = +6dB。

### G6. MP3 解码器未注册（"Decoder MP3 not registered"）

- **现象**：点发音 `AUDIO_DEC: Decoder MP3 not registered` + `ret -7`。
- **根因**：esp_audio_codec 的 simple_dec **默认注册表不含 MP3**（只有 WAV/M4A/TS/OGG），移植时漏调 `esp_mp3_dec_register()`。
- **修复**：启动时依次 `esp_audio_dec_register_default()` + `esp_mp3_dec_register()`；最终为彻底绕开注册表不互通问题，改用 `esp_mp3_dec_open/decode/reset/close` 底层直连 API + 开机常驻句柄。

### G7. MP3 流失步（DATA_LACK 丢弃帧尾残片）→ "缺、短、模糊"

- **现象**：解码日志 `解码失败#1 err=-3（DATA_LACK）缓冲余128` 后连续 `err=-1`；音频缺失约 22%、断裂、模糊。
- **根因**：解码器解出一帧后，输入缓冲剩余 128 字节（下一帧开头），解码器报"数据不足"等待续读；代码却执行 `raw.len = 0` **把帧尾残片整段丢弃**——MP3 流失步，后续帧大量解码失败被丢。
- **修复**：区分两类错误：`DATA_LACK` = 需要更多输入（**保留缓冲**，外层继续读）；真坏帧才放弃本批。并补回原版的 `consumed==0` 等待保护。
- **教训**：移植解码循环时，错误码语义必须逐一对照（`DATA_LACK`≠坏帧）；诊断日志（失败计数+缓冲余量）是定位此类问题的关键。

### G8. 装机运维经验（多次复现的固定模式）

- **outcome_unknown / lease lost**：装机写入成功但验收窗口内设备未回连（WiFi 射频栈 30 秒初始化）→ **reconcile 后重跑一次**即成功，无需重建包。
- **--bundle 与 --project 互斥**：`--bundle` 指定包时不能再带 `--project`；设备解析需要项目上下文时改用 `--project + --skip-build`（复用默认路径的现成包）。
- **手打 irisfw**：`prepare_system_update.py`（staging）+ `esp_iris.py bundle build`（打包）两条命令可绕过 CLI 内部的 ninja 二次调用（避开 `/D:/` 缓存错误）。

# 单词/例句发音无声：排查情报与交接说明

- 排查对象：ESP32-S3 / ESP-Mosaico `word_teacher`
- 排查日期：2026-10-26
- 目标：说明“点击发音按钮没有声音”的完整链路、已确认的代码缺陷、仍未确认的边界和可执行的验证方法
- 当前状态：**未刷机、未提交 Git**。工作区里已经有本次排查产生的候选修改，见文末“工作区现状”。

> 结论先说：这不是单点问题。当前代码里至少存在 4 个相互独立的发音缺陷：
> 1. MP3 解码器“常驻句柄”被错误关闭并继续复用；
> 2. 例句文本被加了两次 `s:` 前缀；
> 3. 无 ID3 的 MP3，缓存漏掉最前面 10 字节；
> 4. 缓存坏文件被无限重复读取，重试没有恢复能力。
>
> 另外，**PC 模拟器本来就不播放声音**，如果在模拟器里测，看到无声不是设备 bug。

## 3. 已确认缺陷（按优先级）

## P0：MP3 解码器句柄生命周期错误

文件：`main/wt_voice.c`

### 3.1 设计意图

结构体注释明确写着“MP3 解码器开机常驻”：

```c
// MP3 解码器开机常驻：运行中期内部堆碎片化后再 open 会 NO_MEM。
void *decoder;
```

`open_mp3_decoder()` 也是这个逻辑：

```c
if (voice.decoder) return voice.decoder;
esp_mp3_dec_open(NULL, 0, &voice.decoder);
```

### 3.2 原始错误

解码器由 **MP3 专用接口**创建：

```c
esp_mp3_dec_open(NULL, 0, &voice.decoder);
esp_mp3_dec_decode(decoder, ...);
```

但每次播放结束、以及多个错误分支里，却调用 **通用解码器接口**：

```c
esp_audio_dec_close(decoder);
```

问题有两层：

1. **接口不配套**：`esp_mp3_dec_open()` 返回的是 MP3 直接句柄，官方头文件 `components/esp_audio_codec/include/decoder/impl/esp_mp3_dec.h:50-51` 明确要求配套使用 `esp_mp3_dec_open/decode/close`，不要混用 common API。
2. **关掉后没有清空 `voice.decoder`**：下一次 `open_mp3_decoder()` 看到指针非空，直接把已关闭的句柄返回。结果是第二次点击发音使用无效句柄。

影响路径：

- 第一次播放结束 → 关闭句柄
- 第二次播放 → 直接复用已关闭句柄
- 表现为第二次开始无声、`decode` 失败、`no-audio`，严重时异常
- 网络连接失败、HTTP 非 2xx 后立即重试，也会踩到同一个坏句柄

### 3.3 正确修复方向

不要“关掉再复用”，而是**保留句柄、每次流结束后 reset**，组件已经提供现成接口：

`components/esp_audio_codec/include/decoder/impl/esp_mp3_dec.h:93-109`

```c
esp_audio_err_t esp_mp3_dec_reset(void *dec_handle);
```

头文件注释写明：reset 会重置内部处理状态、清空输入输出缓存，之后可以复用句柄，避免重新 open 的耗时。

推荐封装：

```c
// 句柄由 esp_mp3_dec_open 创建，必须配套使用 MP3 直接接口。
// 每段流结束后 reset，保留启动早期分配的常驻句柄。
static void reset_mp3_decoder(void *decoder)
{
    if (!decoder) return;
    if (esp_mp3_dec_reset(decoder) == ESP_AUDIO_ERR_OK) return;
    ESP_LOGW(kTag, "MP3 解码器复位失败，重新创建");
    esp_mp3_dec_close(decoder);
    if (voice.decoder == decoder) voice.decoder = NULL;
}
```

然后把这些分支统一改为 `reset_mp3_decoder(decoder)`：

- HTTP client 创建失败
- HTTP 连接失败
- HTTP 状态非 2xx
- 正常播放结束

**不要再调用 `esp_audio_dec_close()`。**

### 3.4 为什么它可能表现为“第一次也没声”

如果启动时 `wt_voice_start()` 里 `open_mp3_decoder()` 就失败，`voice.decoder` 会是 NULL，点击后直接返回 `ESP_ERR_NO_MEM`，一次都不会进 HTTP。

工作区现在的 `main/main.c` 已有一条针对这个方向的未提交修改：**把 `wt_runtime_start()` 提前到 WiFi 之前**，注释写的是 WiFi 先占约 50KB 内部 RAM，导致解码器拿不到连续内存。

这条改动是否真的解决了启动期 `NO_MEM`，必须看串口日志确认，不能只靠代码推断。

## P0：例句被加两次 `s:` 前缀

文件：

- `main/wt_model.c:306-310`
- `main/wt_voice.c:433-440`

模型层给例句命令加了一次前缀：

```c
command(m, out, WT_CMD_SPEAK_SENT);
snprintf(out->text, sizeof(out->text), "s:%s", m->view.sent_en);
```

播放器又把收到的文本当原始例句，自己在缓存键里再加一次：

```c
snprintf(key, sizeof(key), "s:%s", sentence);
wt_voice_build_url(true, sentence, url, sizeof(url));
```

结果假设原句是 `This is a book.`：

```text
播放器实际收到：  s:This is a book.
有道请求音频参数： s:This is a book.   （冒号被 URL 编码成 %3A）
缓存键：          s:s:This is a book.
```

这是**不依赖硬件状态就能确认的请求构造错误**。它会稳定造成：

- 单词正常、例句无声或 HTTP 错误
- 错误结果还会被写入一个错误的缓存键

### 正确修复

`main/wt_model.c` 只传原始例句：

```c
command(m, out, WT_CMD_SPEAK_SENT);
snprintf(out->text, sizeof(out->text), "%s", m->view.sent_en);
```

保留 `wt_voice_speak_sentence()` 内部的 `s:` 键前缀，因为那是缓存命名空间，应该只加一次。

### 已验证

在 `pc/wt_model_test.c` 增加了三项断言：

```c
assert(wt_model_action(m, WT_SPEAK_WORD, &cmd));
assert(cmd.kind == WT_CMD_SPEAK_WORD && !strcmp(cmd.text, v.word));

assert(wt_model_action(m, WT_SPEAK_SENT, &cmd));
assert(cmd.kind == WT_CMD_SPEAK_SENT && !strcmp(cmd.text, v.sent_en));
assert(strncmp(cmd.text, "s:", 2));
```

验证结果：

- 修复前：`Assertion failed: cmd.kind==WT_CMD_SPEAK_SENT&&!strcmp(cmd.text,v.sent_en)`
- 修复后：`PASS: book select, home progress fill, resume, mark-known advance, quiz scoring, online guards, teach prompt, double-tap reset`

这说明例句问题已被真实复现并验证，不是猜测。

## P1：无 ID3 的 MP3，缓存漏掉最前 10 字节

文件：`main/wt_voice.c`，`stream_and_play()` 开头。

当前逻辑先手工读 10 字节判断 ID3：

```c
int got = esp_http_client_read(client, voice.input + head_len, 10 - head_len);
...
size_t skip = head_len == 10 ? parse_id3_skip(voice.input, 10) : 0;
...
carried = pending;
```

问题：

- 如果文件有 ID3v2：前 10 字节是标签，跳过不写缓存，合理。
- 如果文件**没有 ID3v2**：这 10 字节就是 MP3 音频数据，网络首播会使用它，但**从未喂给缓存 writer**。
- 后续循环只把 `esp_http_client_read()` 新读到的数据写入缓存。

后果：

- 缓存文件比网络流少了开头 10 字节
- 后续命中缓存时，解码器拿到的数据与首播不一致
- 可能造成某些词“第一次有声，第二次无声”，或缓存回放 decode 失败

修复方向：在确定 `carried = pending` 后，把已经读进缓冲、且不是 ID3 标签的音频数据补写缓存：

```c
carried = pending;
// 无 ID3v2 时，首 10 字节也是 MP3 数据；必须与后续网络字节一起写入缓存。
if (cache_write && carried > 0)
    wt_cache_writer_feed(voice.input, carried);
```

注意：只在 `cache_write` 为 true（本次走网络且 writer 已成功 begin）时写，缓存回放路径不能重复写。

## P1：坏缓存被重复读取，重试没有恢复能力

文件：`main/wt_voice.c`，`play_key_once()` / `play_key()`

当前：

```c
if (wt_cache_has(key) && wt_cache_path(key, path, sizeof(path)))
    cache_source = fopen(path, "rb");
...
esp_err_t err = play_key_once(key, url);
if (err != ESP_OK) {
    ESP_LOGW(kTag, "发音重试一次");
    err = play_key_once(key, url);   // 还是同一个缓存文件
}
```

问题：

- 第一次缓存回放失败后，没有删除缓存
- 第二次仍命中同一个文件
- 所谓“重试一次”只是把坏文件重新读一遍，没有回退网络

缓存模块已有删除接口：

```c
void wt_cache_remove(const char *path);
```

推荐：缓存回放失败且不是取消时，删除坏缓存，让第二次尝试自动走网络：

```c
if (cache_source) {
    fclose(cache_source);
    if (!o.ok && !o.cancelled) {
        char path[96];
        if (wt_cache_path(key, path, sizeof(path))) {
            wt_cache_remove(path);
            ESP_LOGW(kTag, "缓存播放失败，已删除坏缓存，重试将走网络");
        }
    }
}
```

这条修复的前提是先把 P0 解码器生命周期修好；否则解码器坏句柄会被误判成缓存坏，导致把好缓存删掉。

### 相关但未修复的缓存完整性缺陷

1. `main/wt_cache.c:198-214`
   - `wt_cache_writer_feed()` 注释说“写失败不致命，commit 时校验”
   - 但 `wt_cache_writer_commit()` 只做 `fflush/fclose/rename`，没有保存或检查短写状态
   - 就是说：**注释承诺的校验并不存在**，截断文件仍可能被提交

2. `stream_and_play()` 的成功条件
   - 至少有 1 帧 PCM 写入 I2S
   - 读到 EOF
   - 未被取消
   - 没有校验 HTTP 内容长度或完整接收
   - 所以网络提前结束时，仍可能 `ok=1` 并提交不完整缓存

这两条不是“首次点击必然无声”的直接原因，但会制造后续偶发失败，建议一并处理。

## P2：已 open 的 codec 不会再应用新采样率

文件：

- `main/wt_voice.c:109-123`（`audio_set_format()`）
- `managed_components/espressif__esp_codec_dev/esp_codec_dev.c:149-158`

`wt_voice_start()` 已经用 48kHz 打开扬声器：

```c
esp_codec_dev_sample_info_t format = {
    .sample_rate = 48000, .bits_per_sample = 16, .channel = 1};
esp_codec_dev_open(voice.codec, &format);
```

之后 `audio_set_format(rate)` 又调用 `esp_codec_dev_open()`，但依赖实现是：

```c
if (dev->input_opened || dev->output_opened) {
    ESP_LOGI(TAG, "Input already open");
    return ESP_CODEC_DEV_OK;
}
```

结果：

- 第二次 open 直接返回 OK
- 实际采样率没有重新配置，仍是 48kHz
- 对 44.1kHz 源，代码判断不能整数升采，于是按 44.1kHz 写入；实际硬件仍按 48kHz 播
- 更可能造成**音调/速度异常**，不是完全无声，但它属于确定的格式配置问题

修复方向二选一：

1. 统一在 48kHz 输出：对 44.1kHz 做正确的重采样（不是只支持整数倍 2/3）。
2. 每次换格式前显式 `esp_codec_dev_close()`，再 `esp_codec_dev_open()`，并确认真的重配成功。

不要在未验证的情况下简单删除 48kHz 初始化，否则可能让 PA/音量曲线行为再次变化。

- `main/wt_controls.c:4-15`：默认音量 50，但允许保存为 0

## 4. 真机日志分流方法（最重要）

不要凭“没声音”猜。串口日志按下面分支看，能直接定位到层。

### 4.1 启动阶段

| 日志 | 判定 | 下一步 |
|---|---|---|
| `发音通路不可用` | `wt_voice_start()` 失败 | 查上一行返回码，重点看 codec open / 内存 |
| `MP3 解码器打开失败` | `esp_mp3_dec_open()` 失败 | 查内部 RAM、启动顺序、`CONFIG_AUDIO_DECODER_MP3_SUPPORT` |
| `发音解码器不可用，稍后重试打开` | 启动期没有常驻句柄 | 第一次点击会再尝试 open，可能触发 NO_MEM |
| `dec reg: default=... mp3=... common=...` | 解码器注册结果 | 任何非 0 都记录 |

### 4.2 点击发音后

| 日志/现象 | 含义 |
|---|---|
| 只有 `第一次发音需要联网，请先连接网络`，没有 `Word playback` | 模型层离线守卫拦截，根本没进播放器 |
| `设备忙，请稍后重试` | runtime 未 ready 或命令队列提交失败 |
| `扬声器未就绪` | `wt_voice_ready()` false |
| `连接失败: ...` | HTTP/TLS/DNS 阶段 |
| `HTTP 404` | 有道没有该词发音 |
| `HTTP <其他非 2xx>` | 请求 URL / 服务端 / 网络问题；例句同时查 `s%3A` |
| `不支持的流格式: ...` + `detail=format` | 采样率/位深/声道不符合当前播放器假设 |
| `detail=decode` 或 `decoder-buffer`，没有“首帧 PCM 已写入 I2S” | MP3 数据坏、句柄坏、解码器状态坏 |
| `detail=no-audio` | 一帧 PCM 都没成功输出 |
| `写 I2S 失败 N 次` | 已解码出 PCM，故障在 codec/I2S/PA |
| `首帧 PCM 已写入 I2S` 且最终 `ok=1 pcm>0`，但人耳完全无声 | 请求和解码成功，转查实际 I2S 输出、ES8311、PA、音量、硬件连接 |

### 4.3 必须连续测三次

重启设备，音量设 50 以上，连续点同一个单词三次，中间不要做别的操作。记录：

```text
缓存命中: ...
首帧 PCM 已写入 I2S
播放完成: ok=... bytes=... pcm=... detail=...
Word playback: result=...
发音重试一次
```

判定：

- **第一次 ok=1 有声，第二次开始 decode/no-audio**：高度符合 P0 句柄生命周期错误
- **每次都是 `detail=no-audio`，连首帧都没有**：更靠前，查 HTTP/解码器 open/数据
- **每次 `ok=1 pcm>0` 但始终无声**：数据链路成功，别继续查有道，转硬件输出
- **两次日志都 `缓存命中: 同一路径`，中间无 HTTP**：确认“重试”没有恢复能力

## 9. 不要重复踩的坑

1. **不要把 PC 模拟器无声当 bug。**
2. **不要只改 `s:` 前缀就宣布修好**：它只解释例句，不解释所有单词无声。
3. **不要只把 `esp_audio_dec_close` 改成 `esp_mp3_dec_close`**：
   - 这样能避免接口错配，但下一个问题变成“每次都 close，下一次必须重新 open”
   - 运行中期堆碎片化仍可能 `NO_MEM`
   - 正确做法是 reset 常驻句柄
4. **不要在没有日志的情况下改音量曲线**：当前曲线是上一轮针对“PA 静音/极低档”加的，删掉可能引入新问题。
5. **不要连续刷机十几次碰运气**：先按日志分支定位，一次只改一个点。
6. **不要把 `ok=1` 当成有声**：它只证明至少写入了一帧 PCM，不证明喇叭实际发声。

## 10. 一句话交接

发音链路不是按钮没绑定，也不是单纯网络问题。最确定的两个代码错误是：
**MP3 解码器用专用接口打开、却用通用接口关闭且不清空句柄**，以及
**例句被模型层和播放器重复加 `s:` 前缀**。
先把这两个修掉，再用串口日志按 `HTTP → decode → PCM 首帧 → I2S 写失败` 分层验证；
PC 模拟器永远不会有声音，不能作为验收环境。
